Draft Preview tab and PUBLIC_API_URL

teams-app/manifest.json declares a personal staticTabs entry ("Draft Preview") pinned next to the bot's chat, pointing at GET /drafts/latest/view — a read-only HTML page, no JS, 8s meta-refresh. bot.py's card buttons and this tab both need a URL the user's own Teams client can actually reach, which API_URL (the container-internal localhost:8000 address bot.py uses to call main.py within the same container) is not. PUBLIC_API_URL is set separately by scripts/post-deploy.sh after every deploy — the container app FQDN isn't known until then and changes on every fresh re-provision (new resource-name token), the same reason BOT_MESSAGING_ENDPOINT and the manifest's own validDomains/tab contentUrl are all re-resolved there and in install.sh rather than hardcoded.

The preview renders each section's markdown via the markdown library (tables extension), pre-escaped against raw HTML since new_text/an edit instruction can be human-typed. One correction: the orchestrator's LLM sometimes emits a table whose header has fewer columns than its data rows (e.g. evaluation_criteria's "Criterion | Points" header over 3-column rows with a trailing description cell) — GFM table parsers size columns from the header and silently drop the extra cells, so those descriptions were vanishing entirely from the rendered preview. _pad_ragged_tables() normalizes the header/separator to the widest row's column count before handing off to markdown.markdown(), the same fix sharepoint_client.py's _render_md_table() already applies for the Word export path.

Streaming Architecture — Live Card Preview

The bot updates the Teams Adaptive Card in-place after each section completes using Bot Framework's UpdateActivity. This requires NDJSON streams from both FastAPI and the .NET orchestrator.

NDJSON event contract

Event typeEmitterKey fields

Orchestrator streaming endpoint (C#)

// Program.cs — /generate/stream yields NDJSON as each section completes
app.MapPost("/generate/stream", async (RfpRequest request, RfpOrchestrationService orchestrator,
    HttpContext httpContext, CancellationToken ct) =>
{
    httpContext.Response.ContentType = "application/x-ndjson";
    httpContext.Response.Headers.CacheControl = "no-cache";
    var opts = new JsonSerializerOptions { PropertyNamingPolicy = JsonNamingPolicy.CamelCase };

    await foreach (var evt in orchestrator.GenerateSectionsStreamAsync(request, ct))
    {
        await httpContext.Response.WriteAsync(JsonSerializer.Serialize(evt, opts) + "\n", ct);
        await httpContext.Response.Body.FlushAsync(ct);
    }
});

Bot card update pattern (Python)

# bot.py — background task consumes the FastAPI stream
async def _stream_and_update(turn_context, activity_id, params, subtitle):
    completed = []
    async with httpx.AsyncClient(timeout=300) as client:
        async with client.stream("POST", f"{API_URL}/generate/stream", json=params) as resp:
            async for line in resp.aiter_lines():
                event = json.loads(line)

                if event["type"] == "section":
                    completed.append(event["section_key"])
                    card = _progress_card(completed, next_section, subtitle)
                    await turn_context.update_activity(
                        Activity(id=activity_id, attachments=[CardFactory.adaptive_card(card)])
                    )
                elif event["type"] == "gate_result":
                    await turn_context.update_activity(
                        Activity(id=activity_id, attachments=[CardFactory.adaptive_card(
                            _result_card(event, subtitle)
                        )])
                    )

All endpoints use DefaultAzureCredential — no API keys in configuration. The lifespan context manager initializes all SDK clients (AI Search, Foundry, APIM token) at startup.

The Teams result card offers all three review actions: Approve & Save to SharePoint, Reject, and Edit Section (an inline expanding card with a section picker + full-text box) — available regardless of gate pass/fail, since a failed draft is exactly when editing to fix it matters most. Every card also opens with a 📄 Open Draft Preview button (Action.OpenUrl to PUBLIC_API_URL/drafts/{draft_id}/view) so a program officer can see the draft's actual current text without approving first — see the Teams Bot section below for why this needs a separate, externally-reachable URL rather than the container-internal API_URL bot.py already uses for its own calls to main.py.

A section can also be rewritten from a plain typed chat message instead of a card — no separate button, an earlier "AI Edit" ShowCard action was removed once the typed path proved sufficient on its own. bot.py's _extract_section_edit() matches text against an edit verb (edit/change/update/revise/rewrite/modify) plus a known section name, and only runs when _detect_intent() found no other match — so "update this budget for allowable costs" still resolves to Budget Audit, not a stray rewrite. Once matched, GET /drafts/latest resolves "which draft" (chat text carries no draft_id the way a card submission does), then _apply_ai_edit() sends the whole message as the instruction to POST /drafts/{id}/edit/ai, which rewrites the section via _azure_openai_chat (the same helper /classify//review//audit_budget use) and shares _reevaluate_and_persist_edit() with /edit for the gate-rerun/Fabric-archive tail.

APIM AI Gateway

API Management Standard v2 sits between all application code and the unified AI Foundry account. All Azure OpenAI calls route through apim-pubhealth-{token}/openai. There are no API keys or subscription keys anywhere in this path (subscriptionRequired: false) — the gateway is opened up with validate-jwt instead, checking that the caller presents a valid Entra token issued to this app's own shared managed identity for the https://cognitiveservices.azure.com audience, the same token every service already fetches via DefaultAzureCredential. APIM then authenticates onward to the Foundry account with its own SystemAssigned identity.

Token budget

A single llm-token-limit policy applies a 500,000 tokens-per-minute budget, keyed on caller IP rather than per-subscription (there are no subscriptions to key on once subscriptionRequired is off).

Semantic caching is deferred. The current llm-semantic-cache-lookup/-store policies require an Azure Managed Redis instance with the RediSearch module enabled, registered as an APIM external cache — a whole additional paid resource this POC doesn't provision. See the README's POC Limitations table.

Model Routing — Right-Sized Models per Task

All inference routes through APIM. The deploymentId path parameter selects which model deployment on the Foundry account handles the request — no application-layer routing logic required.

Model assignment

TaskModelRationale
RFP section generation gpt-4o (fine-tuned) Creative, long-form drafting; fine-tuned on historical historical RFPs for domain vocabulary and structure
Groundedness scoring gpt-4o-mini Structured 1–5 Likert rubric; ~15× cheaper than GPT-4o with equivalent accuracy on classification tasks
Coherence scoring gpt-4o-mini Same as groundedness — deterministic rubric, not creative reasoning
Parameter accuracy audit gpt-4o Arithmetic comparison (requested amount vs. budget ceiling, duration vs. period limits); structured JSON extraction via function calling
Budget audit gpt-4o Multi-step budget narrative validation with server-side arithmetic verification; GPT-4o used (o3-mini not available in eastus)
Intent classification gpt-4o-mini Low-latency routing decision; single-label classification from a fixed taxonomy
Embeddings (retrieval) text-embedding-3-large 1536-dim vectors; best recall on public health domain corpus in internal benchmarks

APIM routing policy

The deploymentId URL parameter is a matched route parameter in the APIM operation template /deployments/{deploymentId}/chat/completions (and, for embeddings, /deployments/{deploymentId}/embeddings). The policy reads it directly — no custom headers or application code changes needed. With one backend fronting the whole Foundry account, routing is unconditional:

Estimated cost impact

Eval gate runs on every generated RFP (~8 sections × 5 evaluators). Routing groundedness and coherence to gpt-4o-mini reduces evaluation cost by approximately 93% vs. running all evaluation on GPT-4o, with no measurable change in gate accuracy on the evaluation corpus.

Section-tiered generation

Not all 8 RFP sections require the fine-tuned GPT-4o. Three boilerplate sections — reporting_requirements, budget_requirements, and submission_instructions — contain templated, formula-driven content (CFR citations, portal deadlines, allowable cost lists) that gpt-4o-mini produces equivalently at ~15× lower cost. The remaining five sections (Background, Funding Parameters, Eligibility, Scope of Work, Evaluation Criteria) stay on the fine-tuned model where domain grounding matters.

The orchestrator registers both services in the Semantic Kernel and selects by section key:

// RfpOrchestrationService.cs
private static readonly HashSet<string> MiniSections =
[
    SectionType.ReportingRequirements,
    SectionType.BudgetRequirements,
    SectionType.SubmissionInstructions,
];

var serviceId = MiniSections.Contains(sectionKey) ? "mini" : "gpt4o";
var chat = kernel.Services.GetKeyedService<IChatCompletionService>(serviceId);

Prompt caching

All 8 section calls share the same system message: expert persona + RFP parameters + shared grounding context (retrieved once from AI Search before generation begins). By placing this stable content in the system message rather than the user message, Azure OpenAI's automatic prompt caching activates after section 1 — sections 2–8 pay ~50% on prompt tokens for the cached prefix. No code flag or API opt-in is required; caching fires when the prefix is byte-identical across calls.

// System message is stable across all 8 section calls for this request.
// Caching kicks in for sections 2–8 (identical prefix = cache hit, ~50% off prompt tokens).
var systemMessage = $"""
    You are an expert public health laboratory grants writer ...

    RFP PARAMETERS (authoritative — use exact values):
    - Program Area: {request.ProgramArea}
    ...

    GROUNDING CONTEXT FROM SIMILAR RFPs:
    {groundingContext}
    """;

// User message contains only the per-section variable content.
var userMessage = $"""
    TASK: {sectionPrompt}
    SECTION-SPECIFIC CORPUS EXCERPTS: {sectionContext}
    """;

Embedding model

Retrieval uses text-embedding-3-small instead of text-embedding-3-large — 5× cheaper with ~3% quality difference on standard retrieval benchmarks. Benchmark against the full corpus before upgrading to large in production if recall drops measurably.

Evaluation Gate — 5 Dimensions

All five evaluators run independently via direct httpx calls to the Azure OpenAI chat completions endpoint. A draft must pass all five to proceed. Individual failures return dimension-level failure reasons. The azure-ai-evaluation SDK was removed — it pulled in aiohttp, which crashed the FastAPI async event loop in Container Apps.

DimensionEvaluator TypePass ThresholdWhat It Checks
Groundedness AI-assisted (GPT-4o judge) ≥ 0.80 All factual claims traceable to retrieved corpus chunks
Completeness AI-assisted (GPT-4o judge) ≥ 0.80 All 8 required sections present and substantive
Parameter Accuracy Rule-based (exact match) 1.00 Amount, period, sponsor, cost-share match request parameters
Compliance Rule-based (phrase match) ≥ 0.80 Required compliance phrases present; prohibited terms absent
Coherence AI-assisted (GPT-4o judge) ≥ 0.75 Logical flow, consistent terminology, no internal contradictions

Evaluator pattern (direct httpx)

# src/evaluation/evaluators/groundedness.py
async def evaluate(self, query: str, response: str, context: str) -> EvalResult:
    payload = {
        "model": os.getenv("AZURE_OPENAI_MINI_DEPLOYMENT", "gpt-4o-mini"),
        "messages": [
            {"role": "system", "content": GROUNDEDNESS_SYSTEM_PROMPT},
            {"role": "user", "content": f"Context:\n{context}\n\nDraft:\n{response}"},
        ],
        "response_format": {"type": "json_object"},
    }
    async with httpx.AsyncClient() as client:
        resp = await client.post(
            f"{OPENAI_ENDPOINT}/openai/deployments/{MINI_DEPLOYMENT}/chat/completions?api-version=2024-08-01-preview",
            json=payload, headers={"Authorization": f"Bearer {token}"},
        )
    result = resp.json()["choices"][0]["message"]["content"]
    score = json.loads(result)["score"]  # 0.0–1.0 from rubric prompt
    return EvalResult(score=score, passed=score >= self.threshold, reason=...)

Key files: src/evaluation/gate.py, src/evaluation/evaluators/groundedness.py, src/evaluation/evaluators/completeness.py, src/evaluation/evaluators/parameter_accuracy.py, src/evaluation/evaluators/compliance.py, src/evaluation/evaluators/coherence.py.

Content Safety

Azure AI Content Safety is called on all inbound user requests before generation begins. Blocks PII, harmful content, and select-agent references. Integrated in FastAPI lifespan via ContentSafetyClient(DefaultAzureCredential()).

Select agent handling: The compliance evaluator includes a rule that rejects any draft containing select-agent pathogen names in a non-regulatory context. This is a defense-in-depth layer on top of Content Safety — both must pass.

AI Search Index

Index name: pubhealth-rfp-index. HNSW vector fields on content_vector (text-embedding-3-large, 3072 dims) + keyword BM25 on content. Semantic ranker config: pubhealth-rfp-semantic.

Approval flow

Draft upload is user-gated. When the evaluation gate passes, the draft is stored in an in-memory cache (_draft_cache[draft_id] on the FastAPI process) and an Approve & Save to SharePoint button appears in the Teams Adaptive Card. The user clicks it → the bot calls POST /export/{draft_id} → upload_draft_docx() runs → the link is returned to the chat. If the container restarts between generation and approval, the cache is lost and the user sees a 404 (acceptable for a POC; a Redis or Cosmos cache would fix this for production).

Microsoft Fabric / OneLake

Every draft version is archived to OneLake unconditionally, independent of the SharePoint approval flow — the initial generation and every subsequent edit each write a distinct file ({rfp_id}_{draft_id}.md, then _v1.md, _v2.md, ...) to Files/generated-drafts, plus a matching eval-score record to Files/eval-results. SharePoint, by contrast, only ever holds the single most-recently-approved copy (see API Surface above) — Fabric is the full version history, SharePoint is the current approved artifact.

The RFP corpus itself syncs from a SharePoint document library into Files/rfp-corpus via a standalone Fabric Copy Job item running in CDC (Change Data Capture) mode, so new or changed files sync automatically on Fabric's schedule. Two non-obvious configuration requirements, both required regardless of which auth method is used: the connector needs Sites.Selected Graph/SharePoint Online permissions plus a mandatory site-level permission grant (tenant-wide Sites.Read.All/ReadWrite.All do not satisfy it); and the copy must use Binary file format, not the portal wizard's default (DelimitedText), which would parse document contents as CSV and corrupt anything non-tabular (.docx, .md, etc.). Credentials: the workspace's own Fabric-managed identity (WorkspaceIdentity) — ServicePrincipal auth is documented by Microsoft as unsupported for Copy operations (Dataflow Gen2 only).
